Improving Debugging Accuracy
Through Error Analysis Cycles

Targeted instructional adjustments based on formative data increased debugging proficiency by 41% across two instructional cycles.

The Problem
  • Students could write code but could not fix it. 68% produced logic errors they were unable to self-identify or resolve without direct teacher intervention.
  • Visible on every multi-step task. Error rates spiked at the debugging stage — not at concept introduction — indicating a gap in process skill, not content knowledge.
  • It blocked project completion. Students who could not debug independently stalled at stage 3 of 5, compressing time on later, higher-order work.
Students unable to self-debug 68%

Measured at the start of week two via a structured debugging task administered before any direct instruction on error analysis.

The Data

  • Concentration Over two-thirds of students shared the same error type — this is a design problem, not an individual one.
  • Root cause Errors clustered around logic and operators, not syntax — students understand what to write, not how to reason through it.
  • Drop-off point Performance collapsed at the debugging stage of every multi-step task, not at initial code construction.
Instructional Response
  • 01 Introduced contrastive error analysis tasks Data showed students could not distinguish correct from incorrect logic. Side-by-side broken/working code pairs forced explicit comparison before writing anything new.
  • 02 Added structured debugging checkpoints Errors went undetected because students had no systematic process. A three-step protocol — read, isolate, test — was embedded at the midpoint of each task.
  • 03 Adjusted pacing to isolate the misconception Two sessions were redirected from new content to consolidate logic and operator understanding — the two highest-flagged categories — before advancing.

Instructional Implication
What this reveals
Error patterns are design signals

When two-thirds of a class share the same error, it exposes a gap in instructional sequence — not student ability. Formative data made that visible before it compounded into failed projects.

Across classrooms
Contrastive analysis transfers by domain

Presenting broken work before correct models works wherever process skill matters — not just CS. Any CTE program requiring sequential decision-making can apply this cycle without subject-specific expertise.

Scalable use
The cycle, not the content, is the system

Problem → data → targeted adjustment → measured result is a replicable protocol. It requires one formative checkpoint, one clear decision rule, and willingness to redirect pacing based on evidence.
